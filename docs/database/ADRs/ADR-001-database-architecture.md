# ADR-001: 采用单数据库 + 垂直分表架构

## 状态
**已接受**

## 日期
2026-04-05

## 背景

PaperCrawler需要存储多种类型的数据（用户、论文、爬虫任务、AI对话），每种数据的访问模式和增长速度不同。需要决定是采用单数据库、多数据库、还是分布式数据库架构。

### 业务需求分析

| 数据域 | 记录数 | 增长速度 | 访问模式 | 一致性要求 |
|-------|-------|---------|---------|-----------|
| **用户数据** | < 10万 | 慢 | 随机读写 | 强一致性 |
| **论文数据** | < 100万 | 中 | 读多写少 | 最终一致性 |
| **爬虫任务** | < 100万 | 快 | 队列消费 | 最终一致性 |
| **AI对话** | < 100万 | 中 | 时间序列 | 最终一致性 |

### 技术约束

- 团队规模：5-10人
- 预算：有限（< $2000/月）
- 时间：7周实施周期
- 技术栈：MySQL 8.0+, Redis 6.0+

## 决策

**采用单数据库 + 垂直分表架构**，在同一MySQL实例中按业务领域组织表结构。

### 架构图

```
PaperCrawler Database (Single Instance)
├── User Domain (用户域)
│   ├── users (7条记录)
│   ├── user_sessions (2条记录)
│   └── vip_subscriptions
├── Paper Domain (论文域)
│   ├── papers_core (12条记录)
│   ├── papers_extended
│   ├── papers_user_data
│   ├── journals
│   ├── authors
│   └── paper_authors
├── Crawler Domain (爬虫域)
│   ├── crawler_templates
│   ├── distributed_crawl_tasks
│   ├── crawler_workers
│   └── scheduled_crawl_tasks
├── AI Domain (AI域)
│   ├── ai_conversations
│   ├── ai_messages
│   └── ai_parsing_cache
└── Analytics Domain (分析域)
    ├── search_history
    ├── admin_audit_logs
    └── system_statistics
```

### 关键设计原则

1. **垂直分表**: 按访问频率拆分表（核心表 + 扩展表 + 用户数据表）
2. **域内聚**: 相关表放在同一域（如论文域、爬虫域）
3. **索引优化**: 为每个域的常见查询模式优化索引
4. **缓存分层**: 三级缓存（本地 + Redis + 数据库）

## 替代方案

### 方案A: 单数据库宽表（未采纳）

**描述**: 所有字段放在一张宽表中

**优势**:
- ✅ 查询简单（无需JOIN）
- ✅ 易于维护

**劣势**:
- ❌ 大量冗余字段（用户数据每条记录重复）
- ❌ 缓存效率低（整个行缓存）
- ❌ 锁竞争严重（更新任何字段都锁整行）
- ❌ 扩展困难（添加字段影响所有查询）

**为什么不选择**:
- 用户个性化数据（收藏、笔记）不应放在论文主表
- AI生成的大文本字段影响查询性能

### 方案B: 多数据库（未采纳）

**描述**: 按域拆分为多个数据库实例

**优势**:
- ✅ 故障隔离（一个库故障不影响其他）
- ✅ 独立扩展（论文库可以单独扩容）
- ✅ 性能隔离（爬虫不影响用户查询）

**劣势**:
- ❌ **跨库事务复杂**（需要分布式事务）
- ❌ **运维成本高**（多个实例备份、监控）
- ❌ **开发复杂度高**（需要数据访问层路由）
- ❌ **成本高**（多个服务器实例）

**为什么不选择**:
- 当前规模不需要（单库可支持1000万+记录）
- 跨域事务需求存在（用户购买VIP后提升权限）
- 团队规模有限，运维能力不足

### 方案C: 分布式数据库（未采纳）

**描述**: 使用TiDB、CockroachDB等分布式数据库

**优势**:
- ✅ 无限扩展能力
- ✅ 自动故障转移
- ✅ 强一致性

**劣势**:
- ❌ **学习曲线陡峭**（团队不熟悉）
- ❌ **成本极高**（需要集群）
- ❌ **调试困难**（分布式问题难排查）
- ❌ **过度设计**（当前规模不需要）

**为什么不选择**:
- 杀鸡用牛刀（当前< 100万记录）
- 预算有限（集群成本 > $5000/月）
- 7周实施周期无法学习新技术

## 后果

### 积极后果

1. **简化开发**
   - 无需考虑分布式事务
   - ACID事务保证数据一致性
   - SQL JOIN简单直接

2. **降低成本**
   - 单服务器（~$200/月）
   - 备份和监控简单
   - 无需分布式专家

3. **快速实施**
   - 7周内可完成
   - 无需学习新技术
   - 现有代码改动最小

4. **满足需求**
   - 单MySQL支持1000万+记录
   - 主从复制支持高并发读
   - 缓存层减轻数据库压力

### 消极后果

1. **单点故障**
   - **影响**: 主库故障导致所有服务不可用
   - **缓解**: 主从复制 + 自动故障切换（30秒内恢复）

2. **扩展上限**
   - **影响**: 单实例性能有限
   - **缓解**: 读写分离（提升3倍读性能）
   - **演进**: 超过1000万记录时迁移到分库分表

3. **资源竞争**
   - **影响**: 不同域争抢CPU/IO资源
   - **缓解**: 资源限制（MySQL Resource Groups）
   - **演进**: 拆分为多数据库

### 风险和缓解措施

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| **主库故障** | 中 | 高 | 主从复制 + 自动切换 |
| **性能瓶颈** | 高 | 中 | 读写分离 + 缓存 + 索引优化 |
| **磁盘满** | 中 | 中 | 分区表 + 数据归档 + 监控告警 |
| **备份失败** | 低 | 高 | 多重备份（本地 + 云）+ 定期恢复测试 |

## 实施计划

### 阶段1: 数据库初始化（1周）

**任务**:
1. 执行现有迁移脚本（001-010）
2. 创建用户域表
3. 创建论文域表（垂直分表）
4. 创建爬虫域表
5. 创建AI域表

**验收标准**:
- 所有表创建成功
- 索引创建成功
- 外键约束正确

### 阶段2: 应用层适配（2周）

**任务**:
1. 更新DatabaseModule支持垂直分表查询
2. 实现ReadWriteDatabaseRouter读写路由
3. 更新业务逻辑使用新表结构
4. 实现缓存层（本地 + Redis）
5. 添加数据迁移脚本

**验收标准**:
- 所有测试通过
- 查询性能提升2倍以上
- 缓存命中率 > 70%

## 演进路径

### 当前架构（0-100万记录）

```
单数据库 + 垂直分表 + 读写分离 + 三级缓存
├── MySQL Master (Write)
├── MySQL Slave (Read)
└── Redis Cache
```

### 演进阶段1: 按域拆分数据库（100万-1000万记录）

**触发条件**:
- 单表记录 > 500万
- 并发用户 > 5000
- 主库CPU/IO > 80%

**架构**:

```
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│  User Database   │  │ Paper Database   │  │ Crawler Database │
│  (users, auth)   │  │ (papers, journals)│ │ (tasks, workers) │
└──────────────────┘  └──────────────────┘  └──────────────────┘
        │                      │                      │
        └──────────────────────┼──────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │  Global Cache       │
                    │  (Redis Cluster)    │
                    └─────────────────────┘
```

**影响**:
- ✅ 故障隔离（爬虫故障不影响用户）
- ✅ 独立扩展（论文库可以单独扩容）
- ⚠️ 需要分布式事务（跨库用户权限）

### 演进阶段2: 分库分表（1000万+记录）

**触发条件**:
- 单表记录 > 1000万
- 并发用户 > 10000
- 读写分离无法满足

**架构**:

```
Paper Database Sharding
├── Papers DB Shard 0 (user_id % 10 == 0)
├── Papers DB Shard 1 (user_id % 10 == 1)
├── ...
└── Papers DB Shard 9 (user_id % 10 == 9)
        │
    Sharding Router
        │
    Application Layer
```

**影响**:
- ✅ 水平扩展能力
- ⚠️ 跨分片查询复杂
- ⚠️ 数据迁移成本高

### 演进阶段3: 微服务 + 独立数据库（团队 > 20人）

**触发条件**:
- 团队规模 > 20人
- 预算充足（> $10000/月）
- 业务复杂度高

**架构**:

```
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│  User Service   │  │ Paper Service   │  │ Crawler Service │
│  + User DB      │  │ + Paper DB      │  │ + Crawler DB    │
└─────────────────┘  └─────────────────┘  └─────────────────┘
        │                      │                      │
        └──────────────────────┼──────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │  API Gateway        │
                    │  + Message Bus      │
                    └─────────────────────┘
```
