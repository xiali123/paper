# main.cpp 重构风险评估矩阵

## 风险等级定义

- 🔴 **高风险**: 可能导致系统不可用或数据丢失，需要特别关注
- 🟡 **中风险**: 可能导致功能异常或性能下降，需要仔细测试
- 🟢 **低风险**: 影响范围小或容易修复，正常处理即可

---

## 1. 认证系统迁移

### 风险 ID: AUTH-001
**描述**: 密码哈希算法变更导致现有用户无法登录
**等级**: 🔴 高风险
**影响范围**: 所有需要认证的功能
**概率**: 中等（30%）
**影响**: 用户无法登录，系统不可用

**缓解措施**:
1. 实现双重密码验证（先尝试新算法，失败后尝试旧算法）
2. 用户登录成功后自动升级密码哈希
3. 详细的日志记录，方便排查问题
4. 分阶段发布，先在测试环境验证 1 周
5. 保留旧代码分支至少 1 个月

**测试策略**:
- 单元测试：测试新旧密码哈希算法
- 集成测试：测试登录流程（新用户、老用户）
- 回归测试：验证所有需要认证的 API

**回滚方案**:
- 保留旧密码验证代码
- 配置开关，快速切换回旧算法
- 数据库备份，防止密码哈希损坏

---

### 风险 ID: AUTH-002
**描述**: Session 存储从内存迁移到数据库导致性能下降
**等级**: 🟡 中风险
**影响范围**: 所有需要 Session 验证的请求
**概率**: 中等（40%）
**影响**: 响应时间增加 10-50ms

**缓解措施**:
1. 实现 Session 缓存（Redis 或内存缓存）
2. 数据库连接池优化
3. Session 查询添加索引
4. 批量 Session 验证
5. 性能基准测试（迁移前后对比）

**测试策略**:
- 性能测试：模拟 1000 并发用户
- 负载测试：持续运行 24 小时
- 内存泄漏测试

**回滚方案**:
- 配置开关，切换回内存 Session
- 保留内存 Session 代码作为后备

---

### 风险 ID: AUTH-003
**描述**: Token 生成逻辑变更导致客户端 Token 失效
**等级**: 🟡 中风险
**影响范围**: 所有已登录用户
**概率**: 低（10%）
**影响**: 用户需要重新登录

**缓解措施**:
1. 保持 Token 格式兼容
2. Token 版本标识，支持多版本共存
3. 长过期时间（30 天）给用户缓冲
4. 提前通知用户系统升级

**测试策略**:
- 兼容性测试：新系统验证旧 Token
- 回归测试：验证所有使用 Token 的 API

**回滚方案**:
- 保留旧 Token 验证逻辑
- Token 版本降级开关

## 2. 数据库初始化迁移

### 风险 ID: DB-001
**描述**: 配置文件读取失败导致无法连接数据库
**等级**: 🔴 高风险
**影响范围**: 所有数据库操作
**概率**: 低（10%）
**影响**: 系统无法启动

**缓解措施**:
1. 配置文件验证（启动时检查）
2. 默认配置作为后备
3. 详细的错误提示（缺少哪个配置项）
4. 配置文件示例和文档
5. 环境变量支持（作为后备）

**测试策略**:
- 单元测试：配置文件解析
- 集成测试：测试各种配置错误场景
- 验收测试：验证配置文件示例可用

**回滚方案**:
- 保留硬编码配置作为后备
- 配置文件损坏时自动使用默认配置

---

### 风险 ID: DB-002
**描述**: 表创建逻辑迁移到 Migration 后执行顺序错误
**等级**: 🔴 高风险
**影响范围**: 数据库 Schema
**概率**: 中等（20%）
**影响**: 表创建失败或外键约束错误

**缓解措施**:
1. Migration 版本号和依赖关系管理
2. 执行前检查 Migration 状态
3. Migration 执行日志
4. Dry-run 模式（预演不实际执行）
5. 数据库备份（执行前自动备份）

**测试策略**:
- 单元测试：每个 Migration 脚本
- 集成测试：从空数据库开始完整迁移
- 回归测试：验证 Migration 后数据完整

**回滚方案**:
- Migration 版本号降级
- 恢复数据库备份
- 手动执行 SQL 脚本

---

### 风险 ID: DB-003
**描述**: 连接池配置变更导致连接泄漏
**等级**: 🟡 中风险
**影响范围**: 长时间运行的系统
**概率**: 低（10%）
**影响**: 数据库连接耗尽，系统无法响应

**缓解措施**:
1. 连接池监控（活跃连接、空闲连接）
2. 连接超时自动回收
3. 连接泄漏告警
4. 定期健康检查
5. 压力测试（长时间高并发）

**测试策略**:
- 压力测试：持续运行 48 小时
- 内存泄漏检测
- 连接池监控测试

**回滚方案**:
- 连接池配置参数回滚
- 重启服务清理连接

## 3. 业务 API 迁移

### 风险 ID: API-001
**描述**: JSON 响应格式细微变化导致前端解析错误
**等级**: 🟡 中风险
**影响范围**: 所有前端调用
**概率**: 中等（30%）
**影响**: 前端显示错误或功能异常

**缓解措施**:
1. API 契约测试（使用 Schema 验证）
2. JSON 格式严格检查（类型、字段名）
3. API 版本化（v1 保持兼容，v2 可以变更）
4. 前后端联调测试
5. Beta 测试（小范围用户先体验）

**测试策略**:
- 契约测试：JSON Schema 验证
- 集成测试：前后端联调
- 回归测试：所有 API 端点

**回滚方案**:
- API 版本降级（切换回 v1）
- 紧急补丁修复 JSON 格式

---

### 风险 ID: API-002
**描述**: 数据库查询变更导致性能下降
**等级**: 🟡 中风险
**影响范围**: 查询类 API
**概率**: 中等（40%）
**影响**: 响应时间增加 100ms-1s

**缓解措施**:
1. SQL 查询优化（索引、执行计划分析）
2. 查询性能基准测试
3. 慢查询监控和告警
4. 分页限制（防止一次查询过多数据）
5. 缓存热点数据

**测试策略**:
- 性能测试：每个 API 端点响应时间
- 负载测试：并发查询性能
- 数据库性能分析（慢查询日志）

**回滚方案**:
- SQL 查询回滚
- 添加或优化索引

---

### 风险 ID: API-003
**描述**: 路由迁移后路径冲突或 404
**等级**: 🟡 中风险
**影响范围**: 部分 API 端点
**概率**: 低（15%）
**影响**: 特定 API 不可用

**缓解措施**:
1. 路由注册顺序管理
2. 路由冲突检测工具
3. 完整的 API 端点清单
4. 自动化测试（覆盖所有路由）
5. 路由文档（前端参考）

**测试策略**:
- 路由测试：验证所有路由可访问
- 冲突测试：检查路由冲突
- 404 测试：验证错误路由返回 404

**回滚方案**:
- 路由注册回滚
- 保留旧路由作为后备

## 4. 框架和基础设施

### 风险 ID: FRAME-001
**描述**: 模块依赖顺序错误导致启动失败
**等级**: 🔴 高风险
**影响范围**: 系统启动
**概率**: 中等（25%）
**影响**: 系统无法启动

**缓解措施**:
1. 模块依赖关系明确声明
2. 拓扑排序启动（确保依赖先启动）
3. 启动失败时提供详细错误信息
4. 循环依赖检测
5. 启动顺序文档

**测试策略**:
- 单元测试：模块依赖解析
- 集成测试：各种模块组合启动
- 启动顺序测试：打乱模块加载顺序

**回滚方案**:
- 启动顺序配置覆盖
- 保留旧启动逻辑

---

### 风险 ID: FRAME-002
**描述**: ApplicationBootstrap 实现缺陷导致资源泄漏
**等级**: 🟡 中风险
**影响范围**: 长时间运行的系统
**概率**: 低（10%）
**影响**: 内存泄漏、文件描述符泄漏

**缓解措施**:
1. RAII 资源管理（智能指针）
2. 内存泄漏检测工具（Valgrind、AddressSanitizer）
3. 资源清理验证（单元测试）
4. 定期健康检查（内存、文件描述符）
5. 代码审查（关注资源管理）

**测试策略**:
- 内存泄漏测试：运行 24 小时
- 资源监控：内存、文件描述符、线程数
- 压力测试：频繁启动停止

**回滚方案**:
- 回滚到旧启动逻辑
- 定期重启服务（临时方案）

## 5. 向后兼容性

### 风险 ID: COMPAT-001
**描述**: 客户端硬编码 API 路径，迁移后路径变更
**等级**: 🟡 中风险
**影响范围**: 前端、第三方集成
**概率**: 低（10%）
**影响**: API 调用失败

**缓解措施**:

2. 废弃路径重定向（如果必须变更）
3. API 变更日志和通知
4. API 版本化（v1、v2）
5. 长过渡期（至少 3 个月）

**测试策略**:
- 兼容性测试：新旧路径都测试
- 集成测试：前端调用测试
- 第三方测试：如果有外部集成

**回滚方案**:
- 路径重映射
- API 网关层处理兼容性

- 紧急补丁
- 快速回滚到旧版本

## 风险监控计划

### 关键指标监控

1. **系统可用性**
   - HTTP 响应码监控（非 2xx 比例 <1%）
   - API 响应时间（P95 <500ms）
   - 系统启动成功率（>99%）

2. **错误率监控**
   - 5xx 错误率（<0.1%）
   - 数据库连接错误率（<0.01%）
   - 认证失败率（<5%）

3. **性能监控**
   - CPU 使用率（<80%）
   - 内存使用率（<80%）
   - 数据库连接池使用率（<70%）
   - QPS（对比迁移前后）

4. **业务指标**
   - 登录成功率（>95%）
   - API 调用成功率（>99%）
   - 用户活跃度（对比迁移前后）

### 告警规则

| 告警级别 | 条件 | 响应时间 |
|---------|------|---------|
| P0 严重 | 系统不可用（错误率 >50%） | 5 分钟 |
| P1 高 | 关键功能异常（登录失败率 >10%） | 15 分钟 |
| P2 中 | 性能下降（响应时间 >2x） | 30 分钟 |
| P3 低 | 非关键功能异常 | 2 小时 |

## 应急响应计划

### 场景 1: 系统无法启动

**症状**: 重构后服务启动失败

**诊断步骤**:
1. 检查日志文件（启动错误信息）
2. 检查配置文件（是否存在、格式是否正确）
3. 检查数据库连接（网络、认证）
4. 检查模块依赖（循环依赖）

**应急措施**:
1. 切换回旧版本 main.cpp
2. 保留新代码，继续修复
3. 修复后重新测试和发布

---

### 场景 2: 大量用户无法登录

**症状**: 登录失败率飙升

**诊断步骤**:
1. 检查日志（密码验证失败原因）
2. 检查数据库（用户表、密码哈希）
3. 检查认证模块（配置、依赖）
4. 检查 Session 存储（数据库连接）

**应急措施**:
1. 启用双重密码验证（新旧算法都尝试）
2. 回滚密码验证逻辑
3. 通知用户清除缓存重新登录
4. 紧急补丁修复

---

### 场景 3: API 响应时间急剧增加

**症状**: P95 响应时间 >2x 基准

**诊断步骤**:
1. 检查数据库慢查询日志
2. 检查模块间通信性能
3. 检查缓存命中率
4. Profiling 找出瓶颈

**应急措施**:
1. 回滚性能回归的代码
2. 优化慢查询（添加索引、重写 SQL）
3. 启用缓存
4. 扩容数据库、服务器

---

### 场景 4: 数据损坏或丢失

**症状**: 数据库表损坏、数据丢失

**诊断步骤**:
1. 检查数据库错误日志
2. 检查 Migration 执行记录
3. 检查备份文件
4. 数据完整性检查

**应急措施**:
1. 立即停止服务（防止继续损坏）
2. 恢复最近的数据库备份
3. 分析损坏原因
4. 修复后重新迁移

## 总结

### 风险统计

| 风险等级 | 数量 | 占比 |
|---------|------|------|
| 🔴 高风险 | 6 | 35% |
| 🟡 中风险 | 10 | 59% |
| 🟢 低风险 | 1 | 6% |
| **总计** | **17** | **100%** |

### 关键成功因素

1. **充分的测试**: 单元、集成、E2E、性能、安全测试
2. **分阶段发布**: 先测试环境，再生产环境
3. **监控和告警**: 实时监控关键指标
4. **快速回滚**: 保留旧代码，准备回滚方案
5. **文档和沟通**: 团队充分了解变更

### 建议

1. **优先处理高风险项**: 认证系统、数据库初始化
2. **增量迁移**: 一次迁移一个模块，降低风险
3. **自动化测试**: 建立完整的 CI/CD 流程
4. **灰度发布**: 先小范围用户，再全量发布
5. **保留后备方案**: 旧代码至少保留 1 个月
